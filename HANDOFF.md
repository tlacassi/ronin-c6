- App runtime no longer reads a checkout, SDK, Python installation or sdkconfig. Resources contain firmware images + SHA-256 manifest and pinned official esptool 5.6.0 executables/runtimes for Intel/Apple Silicon, licenses and corresponding source archive.
- Wi-Fi is loaded from the SDK's persistent station configuration. Native USB provisioning changes it without rebuilding/flashing; no password is returned or logged. Wi-Fi changes invalidate movement sessions. Flash leaves NVS/presets intact.
- Dedicated generic build uses sdkconfig.standalone.defaults, empty credentials and 4 MB flash. Packaging refuses non-generic credentials. Do not ship the old local build directory.
- Hardware observed: flash of all three images from an app copied outside the repository, hash verification; migration/read of previous SSID; user changed network from the app and confirmed success; final production firmware reconnects to the saved network after flashing/reset. Native status-only client verified that malformed/oversized lines recover and invalid SSID/password lengths do not change the working network.
- USB RX uses the SDK driver; replies use the serialized SDK stdout USB console path. The initial TX ring-buffer approach failed without background log traffic, so it was replaced and revalidated with quiet production logging. Status handshakes are bounded/idempotent; configuration writes are not automatically retried.
- Both bundled tool architectures execute with an empty environment and no SDK/Python PATH. Universal Swift build, code signature verification, native serial pseudo-terminal tests (fragmented/malformed/stale/rejected/timeout/configure) and trigger gesture tests passed. Intel tool startup was checked through Rosetta on the development Mac; Intel USB hardware was not independently tested.
- The Mac and ESP were on different subnets after the user's network change; USB configuration remains usable, while HTTP control requires joining the same network.
